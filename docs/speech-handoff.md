# 句中停顿、打断补传与回答交接

适用工程：ESP32_VoCatXKorvo，ESP-VoCat v1.2，ESP-IDF 6.1。更新于 2026-11-06。

## 问题与证据

用户在一句话中停顿后继续讲话，平台可能先发送 `input_audio_buffer.speech_stopped` 并开始回答。旧代码立即停止 `audio_in`，会截断仍在补传的句首音频。实板日志出现了 `target_ms=1792`、`sent_opus_frames=18`：原本约 1.79 秒的补传只发送约 0.36 秒。`dropped_ms=0` 表示没有记录到保护期间的缓存溢出，不表示整段音频已上传。

2026-11-05 的交接保护又引入了误取消：只要最近人声尚未全部上传，就取消回答。随后实板日志中出现 1040、1400、32、44 ms 的积压，四次均被本地取消；接收到了音频但 `played=0`。特别是 32/44 ms 只是很短的处理与上传延迟，不能作为用户继续讲话的证据。2026-11-06 改为将“需要补传的旧音频”和“回答候选之后新采集并确认的人声”分开判断。日志另有一次网络写超时；本次证据不能确定其原因，也不能将该问题归为已修复。

`confused.eaf` 对应等待回复音频。等待期间显示该动画并不表示重启或网络断开。本轮没有更换动画。

## 模块分工与流程

保留现有 C 模块、事件总线、主任务、AFE 任务和 WS 接收工作任务，不新增工作任务或大音频缓存。

| 模块 | 本轮职责 |
| --- | --- |
| `wake_word.c` | 在原 PCM FIFO 上记录写入/读出/最近人声的采样位置；消费者复制和归还帧在同一短锁内完成。为每轮回答单独观察新采集的人声，旧 FIFO 补传不参与这项确认。等待回复时也检测语音打断。 |
| `audio_in.c` | 只在成功发送 Opus 包后推进已上传位置；支持暂停和恢复，保留当前帧余量、未满 20 ms 的编码输入、编码器和补传计数。 |
| `input_handoff.h` | 用采样位置、补传状态和新采集人声的确认结果，决定继续补传、取消抢答或接受回答。复用既有打断人声规则。 |
| `response_stream.c`、`ws_service.c` | 平台断句后暂缓播放；主任务按连接代次和本地回合批准。等待期间使用现有有界接收队列；取消后继续丢弃旧音频并处理结束边界。 |
| `app_main.c` | 串行执行输入交接、上传暂停、发送取消、等待确认和恢复；迟到事件不能直接调用 `audio_in_stop()` 关闭新输入。 |

收到平台断句后的三种情况：

1. **仍有未上传的人声、受保护的预录音，或尚未确认的新讲话候选**：继续上传，暂缓播放回答，不发送取消。旧音频积压不论是 32 ms 还是 1400 ms，都只意味着需要补传；没有人为设置“小积压接受、大积压取消”的门槛。交接超过 10 秒仍不能完成时进入会话恢复，避免无期限停留。
2. **回答候选之后新采集的人声达到确认条件**：先让上传任务暂停在可恢复位置，再取消提前生成的回答。等待取消确认时，AFE 继续录音；确认后恢复同一个上传任务，先发送剩余历史，再衔接后续音频。确认要求 AFE VAD 判为人声、能量至少 12000，在不超过 640 ms 的窗口内累计 480 ms 合格人声，连续间隙不超过 96 ms；复用既有打断规则，不是语义识别。
3. **输入已经交接完成，也没有待确认的新讲话**：暂停上传后再次核对采样位置、新人声状态和回答的连接代次/回合。暂停期间又有输入需要发送时恢复原任务并继续补传；确认可以交接才停止上传、进入等待回复状态，允许接收工作任务播放。若批准时连接或回合已变化，旧批准失效，重新处理当前输入。

新人声观察从主任务取得当前回答候选时开始，只统计之后 AFE 实际采集的帧。每次观察都有独立 ID；结束会话、恢复会话、完成交接、取消或清空 FIFO 时结束或使其失效，防止旧回合的确认结果用于新回答。

等待首包音频时，原有 AFE/VAD 打断判定也会运行，不再要求喇叭已经出声。实际起播后仍保留 1200 ms 起播保护、480 ms 人声确认和既有能量/短隙规则。

采样位置按 16 kHz 计算，计数使用 32 位模运算；在约 10 秒有界 FIFO 的距离范围内可跨回绕比较。清空缓存必须先停止上传，并同步复位位置。用于记录待上传人声位置的条件是 AFE VAD 为人声且处理后能量至少为 2500；它仅用于补传进度，不能替代能量 12000、累计 480 ms 的取消确认。

恢复监听时，先切换 AFE 到 LITE 模式，再启动上传；返回待唤醒时，先确认上传已停止，再切换模式和清空 FIFO。这样避免 AFE 模式切换复位采样位置时，上传任务仍在使用上一组计数。

锁不覆盖网络等待：缓存锁只保护复制/计数，上传锁只保护成功发送位置；暂停的最长等待为 2 秒，单次 WS 发送原有超时为 1 秒。主循环查询待交接回答采用非阻塞播放锁，避免播放忙时拖住触屏和超时检查。

## 日志与验证

- `Reply held ... unsent_speech_ms=... replaying=...; draining input, no cancel`：等待补传或新人声候选判定，不取消。该时间是尚未上传到最近人声末端的音频跨度，可能包括间隙；每轮等待只记录一次。
- `Fresh speech confirmed after reply offer ...; cancel response, retain input`：回答候选之后，新采集的人声已通过确认，取消抢答并保留输入。
- `Playback stopped (unfinished input)`：已确认的后续讲话在输入交接期间触发取消，与手动/播放时语音打断区分。
- `Barge-in replay sent ...`：原有补传完成日志；暂停恢复不会重新开始或重复发送此前成功的包。
- `Input handoff complete ...`：输入交接完成，允许播放回复。

桌面回归：先由组件管理器安装项目依赖，再运行：

```powershell
python scripts/check_audio.py --cc <本机tcc.exe路径>
```

回复测试调用生产 JSON 解析器、回复生命周期、交接规则和打断规则，覆盖提前结束、延后批准、取消后旧包、重复/过时批准、计数回绕、等待首包时的打断与起播保护。上传测试直接运行生产 `audio_in.c` 的任务/分包/暂停恢复逻辑，用顺序 PCM 样本验证不重复、不跳样，并覆盖半包暂停、同一补传两次暂停、发送失败和暂停时退出。

新增回归覆盖日志里的 32/44/1040/1400 ms 积压：均先补传，排空后接受回答，取消次数为零；覆盖 1792 ms 预录音、单帧噪声、非人声高能量、弱人声、480 ms 确认和短间隙。`scripts/check_audio.py` 还会从 `app_main.c` 提取生产交接上下文及 `reset_input_handoff`、`process_reply_offer` 原函数，替换其外部服务后执行，检查暂停时来新帧、回答轮次变化、批准失败、暂停/上传故障和 10 秒等待上限，没有另写一份交接流程代替生产代码。

本次主机检查通过：回复解析/生命周期 413 项，上传样本/生命周期 97874 次断言，交接规则/序列 341 项，生产主任务交接 268 项。其中上传断言包含大量逐样本检查，不能理解成 97874 种不同场景。ESP-IDF 6.1 编译通过，应用分区余量 20%。本地验证记录存于 `work/handoff-regression-20261106/`；该目录不作为固件源码提交。

`tests/audio_host` 只替换 RTOS、麦克风和编码器/网络依赖，是单线程确定性调度注入；其原子操作替身不验证多核内存序。固件始终使用 SDK 的原子操作和锁。主机结果不能替代真实 AEC、网络时序和听感验证。

实板建议按以下顺序测试：

1. 普通问答、多轮连续对话，确认回复尾音和恢复聆听正常。
2. 播放时用短句打断，检查补传完成及识别结果；再测试长句和句中停顿。
3. “帮我查一下……明天的新闻”，分别在平台尚未出声、刚出声和持续播放时继续说后半句。
4. 连续两次打断、聆听时触屏结束、再次唤醒，确认输入/取消状态不会遗留。
5. 不讲话时播放长回答，检查误打断；断网再恢复，检查旧连接事件不影响新会话。

## 平台边界

本地没有修改平台 VAD 参数或发送未经确认的会话配置。句末静音时间、语义断句仍需平台优化，不能保证设备完全阻止平台把长停顿拆成两次提问。480 ms 确认是本地抗误触发策略，短于该时长的后续语句不保证触发交接取消。

协议中的原始二进制音频没有响应 ID，部分 `speech_stopped` 也缺少足够的输入身份。本轮用连接代次、本地回合和真实未上传输入保护交接，不能凭设备日志恢复平台未提供的身份。平台仍需保证取消确认之后不混入旧回答音频，并发送可靠的最终音频结束事件；已执行的工具动作也不能由取消语音回答自动撤销。

本轮未烧录；完成固件编译和主机回归后，实际连续说话、停顿容忍度和声音效果仍需上述实板测试。
